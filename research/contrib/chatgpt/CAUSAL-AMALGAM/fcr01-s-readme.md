- **Narrow question:** Can independently selected pre-existing native transition experts and terminal-reward experts recombine on entirely *public* witnessed two-stage episodes while preserving the original native checkpoint and avoiding a shared-context retrieval failure?
- **Implementation:** `factorized_context_readout.py` wraps an immutable `NativeEpisodeExperience` snapshot; stores two exact-Fraction distributions over the same existing context experts. Each `advance(native_successor)` requires exactly one extra native-admitted ledger event, unchanged expert provenance and context identity, and computes both likelihoods with **the prior snapshot** before rebinding. It never writes to native or reads source-only labels; `checkpoint` and cold `restore` bind to the hash of the native bytes and context-expert identities. Same pre-existing `REFRESH_RATE=1/32` if activated. Novel-expert *creation* remains exclusively native-owned.
- **Deliberate limits:** This is not yet historically replay-trained as two independent posteriors: it starts both from the existing, potentially already joint-trained native posterior, and only separates **subsequent** evidence. Existing context segmentation may be inadequate; a correlated true joint mechanism can defeat factorization. A native reset/resegmentation or unexplained expert change is rejected rather than silently bridged. Context counts and exact Fractions can exceed capacity/CPU limits: measure before further science.
- **Negative controls:** transition-only evidence, reward-only evidence, old-module recombination, missing new module, correlated counterexample, immutable native bytes, identical cold forecast, malformed/replayed episodes, wrong checkpoint/parent/tampered scientific flags, expert-count drift, original refresh policy.
